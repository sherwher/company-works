# Workflow — Dev-ready Review (30분 게이트)

UI/HTML 또는 기획 산출물을 개발 착수 가능 상태(`trust_level: L3`)로 승격시키는 표준 회의.
산출물 신뢰 등급은 [`shared/outputs.md`](../shared/outputs.md) §AI 산출물 신뢰 등급 참조.

## 목적

"기획팀이 다 만들어 줬는데 개발이 또 리뷰?"와 "AI가 뽑은 raw 결과를 그대로 받기는 불안하다" 사이의 충돌을 **명시된 게이트**로 흡수한다. 리뷰 그 자체가 아니라 **리뷰의 이름·목적·통과 기준**을 고정하는 것이 본 워크플로의 본질이다.

## 언제 호출하는가

다음 중 하나라도 해당하면 본 회의를 통과해야 다음 단계로 간다.

- 기획/디자인/AI 엔지니어가 산출물에 `trust_level: L2` 라벨을 달고 개발 핸드오프를 요청할 때
- AI 또는 하이브리드(`generated_by != human`)로 만든 산출물이 처음 개발팀에 노출될 때
- 산출물이 부분 화면만 포함하거나 데이터 모델/API 계약이 비어 있는 채로 핸드오프되려 할 때

L1(Draft) 산출물은 본 회의 대상이 아니다. 작성자가 먼저 L2까지 끌어올린다.

## 참여자 (3인 + 옵션 1인)

| 역할 | 인원 | 책임 |
|---|---|---|
| 작성자 (PM/기획/디자인 중 1) | 1 | 문제·범위 설명, 역추적 설명 책임 |
| 개발 리드 (BE 또는 FE) | 1 | 도메인·데이터·API 누락 점검, 구현 가능성 판정 |
| 디자인 또는 다른 기획 | 1 | UX 흐름·예외 상태 점검 |
| QA | 옵션 | 테스트 가능성 사전 확인 |

3인 이상 부르지 말 것. 의사결정 속도가 본 회의의 핵심이다.

## 입력

- 대상 산출물 (메타데이터 + SSOT 6섹션 포함, [`shared/outputs.md`](../shared/outputs.md))
- Dev-ready 체크리스트 (작성자가 자가점검 후 첨부)
- 관련 PRD 또는 기획 브리프 링크

## 진행 (30분 고정)

```
00:00–05:00  작성자: 문제와 범위 설명 (Why/What/Out-of-scope)
05:00–10:00  HTML/UX 흐름 확인 (주요 경로 + 예외 상태)
10:00–20:00  개발 리드: 도메인·데이터·API 누락 점검
              · 엔티티·관계·상태 전이
              · 필수/선택 필드 + 검증 규칙
              · 권한 모델
              · API 초안 (동기/비동기, 에러 코드)
              · DB 영향 / 마이그레이션 필요 여부
20:00–25:00  미확정 정책 결정 또는 보류 표시
25:00–30:00  Dev-ready 판정 + Decision Log 작성
```

회의 중 작성자가 "AI가 짜줬어요"로 답하는 순간, 해당 항목은 자동으로 미검증 처리한다 (역추적 설명 의무, [`shared/outputs.md`](../shared/outputs.md)).

## 판정 (3가지)

| 판정 | 의미 | 후속 |
|---|---|---|
| **Ready** | `trust_level: L3` 부여, 개발 착수 가능 | BE/FE 워크플로 진입 |
| **Ready with constraints** | 일부 범위만 L3 부여, 나머지는 보류 | 범위 명시 후 부분 착수 |
| **Not ready** | 누락 항목이 많음 | 보완 후 재검토 (재회의는 30분 고정) |

판정 결과는 산출물의 `validation.engineering_review`와 `trust_level`에 반영하고, Decision Log(`DEC-YYYYMM-XXX`)를 1건 생성한다.

## 출력

1. 산출물 메타데이터 갱신 (`trust_level`, `validation.*`, `known_missing` 보완)
2. Decision Log 1건 — 판정 결과·제약·미확정 정책 결정
3. (Not ready 시) 보완 항목 체크리스트 + 재검토 일정

## 참여자에게 전달할 메시지

**기획·디자인에게**:
> HTML 시안은 사용자 경험의 표현이지 DB/API/도메인 계약이 아니다. 본 회의는 기획을 다시 하자는 게 아니라 화면을 시스템으로 변환하는 필수 게이트다. 본인이 만든(또는 만들게 한) 모든 요소는 역추적 설명이 가능해야 한다.

**개발에게**:
> 핸드오프된 산출물을 raw로 보지 말고 변환 입력으로 다룬다. "다시 리뷰 필요"가 아니라 어느 항목이 누락되었는지 Dev-ready 체크리스트로 피드백한다. `trust_level: L3` 라벨이 붙은 것만 스프린트에 투입한다.

## 안티패턴

- 회의를 30분 이상 끌기 (속도 잃으면 게이트 무력화)
- 4명 이상 부르기 (의사결정 분산)
- 판정을 "다음에 다시"로 미루기 — Not ready라도 "무엇이 빠졌는지" 명시
- 회의 결과를 메타데이터/Decision Log에 반영하지 않기
- L1 상태에서 본 회의 부르기 — L2 자가 검증 후 진입
