# VERSIONING — 템플릿 갱신과 프로젝트 동기화

본 문서는 **템플릿 메타 리포의 버전 관리**와 **그것을 도입한 프로젝트가 어떻게 동기화하는가**를 정의한다.
운영 구조는 [`OPERATIONS.md`](./OPERATIONS.md), 도입 절차는 [`SETUP.md`](./SETUP.md).

> 핵심: 템플릿은 시맨틱 버전을 갖고, 프로젝트는 어떤 버전을 따르는지 핀(pin)한다. 갱신은 자동 머지가 아니라 **CHANGELOG를 보고 골라서 머지**한다.

---

## 1. 시맨틱 버전 규칙

`MAJOR.MINOR.PATCH`.

| 변경 종류 | 버전 증가 | 예시 |
|---|---|---|
| **MAJOR** | 호환성 깨짐 | 포지션 R&R 경계 변경, 권한 등급 정의 변경, AC 매핑 규칙 변경 |
| **MINOR** | 기능 추가, 호환성 유지 | 새 포지션 추가, 새 워크플로 추가, 양식 필드 추가 |
| **PATCH** | 문서 보완, 오타, 예시 추가 | 안티패턴 사례 추가, 게이트 설명 보강 |

템플릿 메타 리포 루트에 `VERSION` 파일을 둔다.
```
1.0.0
```

---

## 2. CHANGELOG

템플릿 메타 리포 루트에 `CHANGELOG.md`를 둔다. **Keep a Changelog** 형식.

```
# CHANGELOG

## [Unreleased]
### Added
- ...

## [1.1.0] - 2026-06-15
### Added
- agents/data-engineer.md (신규 포지션)
### Changed
- agents/backend.md: 운영 마이그레이션 권한 명시 강화

## [1.0.0] - 2026-05-04
### Added
- 초기 릴리스
```

릴리스 시:
1. `[Unreleased]` 항목을 새 버전 헤더로 이동
2. `VERSION` 파일 갱신
3. git tag 생성 (`v1.1.0`)

---

## 3. 프로젝트 측 버전 핀

각 프로젝트의 `CLAUDE.md` 상단 메타데이터에 사용 중인 템플릿 버전을 명시한다.

```
---
template_version: 1.0.0
template_origin: <메타 리포 URL>
last_synced: 2026-05-04
---

# CLAUDE.md - 사내 AI 에이전트 협업 규약 (공통)
...
```

이 메타데이터가 있어야 갱신 시 어떤 버전에서 출발해야 하는지 알 수 있다.

---

## 4. 프로젝트 갱신 절차

템플릿이 `1.0.0 → 1.1.0`으로 올라갔을 때:

### 4.1 CHANGELOG 검토
1. 메타 리포 `CHANGELOG.md`에서 `1.0.0`과 `1.1.0` 사이 항목을 모두 읽는다.
2. 항목별로 **이 프로젝트에 적용 필요한가**를 판단한다.
   - 새 포지션 추가: 우리 프로젝트에 그 포지션이 필요한가?
   - 양식 필드 추가: 기존 산출물도 소급 적용할 것인가, 새 산출물부터인가?
   - R&R 변경 (MAJOR): 영향 받는 진행 중 작업이 있는가?

### 4.2 머지
적용 결정한 항목만 cherry-pick으로 가져온다.
- 메타 리포 디렉터리에서 해당 파일을 복사 → 프로젝트의 `agents/`, `workflows/`, `shared/`에 덮어쓰기
- **`docs/`는 절대 건드리지 않는다** (살아있는 산출물)
- **프로젝트 오버라이드 섹션**은 보존 (S5)

### 4.3 메타 갱신
- `CLAUDE.md` 상단 `template_version`, `last_synced` 갱신
- Decision Log 작성: `DEC-YYYYMM-XXX-template-sync` (어떤 항목을 적용·미적용했는지)

### 4.4 PR
한 번의 동기화 = 한 PR. 머지 후 팀에 공지.

---

## 5. 프로젝트 오버라이드 규칙

프로젝트가 템플릿 본문을 수정해야 할 때가 있다. 머지 충돌을 막기 위해 **오버라이드 섹션**을 따로 둔다.

### 5.1 오버라이드 위치
각 `agents/<role>.md`, `CLAUDE.md`, `workflows/<flow>.md` 하단에 다음 섹션을 둔다.
```
---

## Project Override

> 본 섹션은 본 프로젝트만의 추가/수정 규칙이다. 템플릿 동기화 시 이 섹션은 보존된다.

- (예) 본 프로젝트의 BE는 운영 마이그레이션을 항상 dry-run + 2명 검토 (L3에서 L3+).
```

### 5.2 금지
- 템플릿 본문(상단 절들)을 직접 수정 금지. 수정해야 하면 메타 리포에 PR을 보낸다.
- 오버라이드로 **권한을 완화**할 수 없다 (강화만 가능). 예: L2 → L3로 강화 OK, L3 → L2 완화 금지.

### 5.3 머지 동작
- 동기화 시 템플릿 본문은 새 버전으로 덮어쓰기, "Project Override" 섹션은 보존.
- 자동화 도구(grep/sed)가 가능하지만, 처음에는 사람이 PR diff로 확인하는 것을 권장.

---

## 6. 메타 리포 변경 절차 (역방향)

프로젝트에서 발견한 패턴을 메타 리포로 올릴 때:

1. 프로젝트의 오버라이드/사례를 정리
2. 메타 리포에 PR 생성
   - `templates/` 본문 변경
   - `CHANGELOG.md`의 `[Unreleased]` 갱신
   - 근거를 `research/` 또는 `lessons/`에 추가 (사례 기반이면 출처 인용)
3. 리뷰어가 다음을 검증:
   - [ ] 변경이 R&R 경계를 침범하지 않는가
   - [ ] 안티패턴(CLAUDE.md S9)을 새로 만들지 않는가
   - [ ] 시맨틱 버전 등급이 적절한가
4. 머지 + 새 버전 릴리스

---

## 7. 동기화 도구 (선택)

소규모 팀: 사람이 CHANGELOG 보고 수동 cherry-pick. 충돌 거의 없음.

대규모 팀 또는 프로젝트 5개 이상: 다음 방식 검토.

| 방식 | 장점 | 단점 |
|---|---|---|
| `git subtree` | 히스토리 보존, 양방향 가능 | 학습 곡선, 충돌 시 복잡 |
| `git submodule` | 명확한 버전 핀 | 사용자 경험 불편 (파일이 별도 위치) |
| 패키지 매니저 (npm/pip) | 버전 핀 자동화 | 마크다운 템플릿엔 과한 도구 |
| 커스텀 sync 스크립트 | 프로젝트 요구에 맞춤 | 유지보수 부담 |

권장: **시작은 수동 + CHANGELOG**, 프로젝트가 5개 넘어가면 `git subtree` 검토.

---

## 8. 호환성 정책

- **MAJOR 변경**: 최소 1개월 사전 공지. 마이그레이션 가이드(`MIGRATIONS/v1-to-v2.md`) 작성.
- **MINOR/PATCH**: 즉시 릴리스 가능. CHANGELOG만으로 충분.
- 진행 중 워크플로가 있을 때 MAJOR 동기화는 위험 → 워크플로 종료 후로 미룬다.

---

## 9. 동기화 체크리스트

- [ ] 메타 리포 CHANGELOG의 `1.x.0 ~ 새 버전` 사이 모두 검토
- [ ] 적용/미적용 결정을 Decision Log로 작성
- [ ] 프로젝트 오버라이드 섹션 보존 확인
- [ ] `template_version`, `last_synced` 갱신
- [ ] 진행 중 산출물 ID·AC가 영향 받는지 검토
- [ ] 한 PR로 머지 + 팀 공지
