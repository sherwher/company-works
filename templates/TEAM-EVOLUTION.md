# TEAM-EVOLUTION — 팀·포지션·에이전트 변화 관리

본 문서는 운영 중인 프로젝트에서 **사람·포지션·에이전트 인스턴스가 추가·변경·제거될 때**의 절차를 정의한다.
운영 구조는 [`OPERATIONS.md`](./OPERATIONS.md), 템플릿 갱신은 [`VERSIONING.md`](./VERSIONING.md).

> 핵심: 한 포지션 = 한 에이전트 = 한 책임 (CLAUDE.md S2 원칙2)을 깨지 않으면서 팀이 성장하게 만든다.

---

## 1. 사람 추가 (담당자 합류)

새 사람이 기존 포지션에 합류할 때.

### 1.1 절차
1. `docs/team.md`에 추가
   ```
   | 이름 | 포지션 | 담당 워크플로 | 합류일 | 비고 |
   |---|---|---|---|---|
   | @kim | BE | full-cycle, feature-add | 2026-05-04 | |
   ```
2. 진행 중 Work Unit 인수: 기존 담당자가 핸드오프 메시지(handoff type)로 이전. 인수자는 진입 체크리스트 통과 후 시작.
3. 에이전트 시스템 프롬프트의 `[Project Context]` 갱신은 불필요 (개인 정보가 아닌 R&R 기반).

### 1.2 온보딩 자료
신규 합류자가 읽어야 할 순서:
1. `CLAUDE.md` (공통 규약)
2. `agents/<자기 포지션>.md` (자기 R&R)
3. `OPERATIONS.md` (운영 구조)
4. `docs/decisions/` 최근 10건 (왜 이렇게 됐는가)
5. 진행 중 산출물 (`docs/<type>/`의 status=draft/reviewed)

---

## 2. 사람 제거 (담당자 이탈)

### 2.1 절차
1. 이탈 1주 전 공지 + 진행 중 Work Unit 목록 정리
2. 각 WU별 인수자 지정 → 핸드오프 메시지 작성
3. 미완료 산출물의 `author` 필드 갱신 (또는 인수자 추가)
4. `docs/team.md`에서 행 제거 또는 "이탈" 표기

### 2.2 검증
- [ ] 이탈자가 owner인 WU가 모두 인수됐는가
- [ ] 이탈자가 작성 중인 `draft` 산출물의 책임자가 명확한가
- [ ] 이탈자가 단독 결정한 미기록 결정이 있는가 → Decision Log 소급 작성

---

## 3. 포지션 추가 (예: Data Engineer 신설)

### 3.1 의사결정
포지션 추가는 **메타 리포 수준의 결정**이다. 한 프로젝트가 임의로 만들면 다른 프로젝트와 협업이 깨진다.

1. 사례를 1~2개 프로젝트에서 검증
2. 메타 리포에 PR (`agents/<new-role>.md` + CLAUDE.md S3 카탈로그 + 영향 받는 워크플로의 게이트)
3. CHANGELOG의 MINOR 항목으로 릴리스
4. 각 프로젝트가 [`VERSIONING.md`](./VERSIONING.md) 절차로 가져감

### 3.2 새 포지션 파일 작성 체크리스트
새 `agents/<role>.md`는 다음을 모두 포함해야 한다 (기존 10개와 일관성 유지).

- [ ] Identity (Role / 권한 상한 / 담당 산출물)
- [ ] R&R (Mission / In-Scope / Out-of-Scope / 에이전트 활용 / DoD)
- [ ] 진입/이탈 게이트 (어느 워크플로의 어느 게이트에 끼어드는가)
- [ ] 산출물 양식 (또는 기존 양식 재사용)
- [ ] 추가 규칙
- [ ] 시스템 프롬프트 절 (CLAUDE.md S8 골격 참조)

### 3.3 워크플로 영향
새 포지션이 끼어드는 워크플로는 게이트가 추가된다. 영향 받는 `workflows/<flow>.md`도 같은 PR에서 갱신.

---

## 4. 포지션 제거

거의 발생하지 않지만 (예: 외주화로 사내 포지션 폐지):
1. 영향 받는 워크플로의 게이트를 재설계 (이전 포지션의 책임을 어디로 보낼지)
2. 메타 리포에 PR (MAJOR 또는 MINOR 등급은 영향 범위에 따라)
3. 각 프로젝트가 동기화 시 진행 중 WU 정리

---

## 5. 에이전트 인스턴스 늘리기 (병렬화)

같은 포지션의 에이전트를 2개 이상 동시에 돌리고 싶을 때.

### 5.1 원칙
**CLAUDE.md S2 원칙2 "한 포지션=한 에이전트=한 책임"** 은 *동일 책임 단위* 에 대한 것이다.
**다른 Work Unit이면 병렬 실행 가능**, 같은 WU에는 항상 1개.

### 5.2 허용 패턴
- BE 에이전트가 동시에 `WU-202605-007 (결제 API)` 와 `WU-202605-008 (환불 API)` 작업 → OK (다른 WU)
- QA 에이전트가 동시에 PR-#101, PR-#102 검증 → OK (다른 PR)
- AI 엔지니어가 모델 A 평가, 모델 B 학습을 병렬 → OK (다른 산출물)

### 5.3 금지 패턴
- 같은 WU에 BE 에이전트 2개가 동시에 코딩 (S2 원칙2 위반)
- 같은 PR을 두 에이전트가 동시에 push (충돌)
- 같은 산출물의 `draft`를 두 에이전트가 동시에 편집 (덮어쓰기)

### 5.4 병렬화 시 운영
- WU별로 작업 디렉터리/브랜치를 분리한다.
- 각 인스턴스의 trace는 WU ID로 태깅한다 (관측성 — CLAUDE.md S2 원칙11).
- 산출물 ID 시퀀스 충돌이 잦아지면 `_INDEX.md` 잠금 또는 사전 예약 제도 도입.

### 5.5 한계
- 한 포지션을 5개 이상 동시 운영하면 핸드오프·검토 부하가 사람을 압도. 그 시점에서는 사람 인원 추가 또는 포지션 분할 검토.

---

## 6. 권한 등급 변경

특정 인원·에이전트에게 임시로 권한을 올리거나 내릴 때.

### 6.1 절차
1. Decision Log 작성 (사유, 기간, 승인자)
2. 영향 받는 `agents/<role>.md`의 Project Override 섹션에 임시 규칙 명시
3. 만료 후 자동 회수 — `.agents/permissions.md`에 만료일 기록

### 6.2 금지
- 영구적 완화는 메타 리포 변경 절차로 (오버라이드로 영구 완화 금지 — VERSIONING.md S5.2).
- L4 권한은 임시라도 사람 승인 + 2차 검토 의무.

---

## 7. 워크플로 변경

### 7.1 게이트 조정
프로젝트가 게이트 조건을 자체 강화/완화할 때:
- 강화: 오버라이드로 가능 (예: G6 통과 조건에 "보안팀 사인오프" 추가)
- 완화: 메타 리포 PR 필요 (안전성 영향)

### 7.2 신규 워크플로 추가
프로젝트 한정이면 `workflows/<custom>.md`를 추가하되 파일명에 `local-` 접두사 (예: `local-hotfix.md`)를 붙여 메타 리포 워크플로와 구분.
패턴이 검증되면 메타 리포에 올린다.

---

## 8. 변경 이력 추적

모든 팀·포지션·에이전트 변경은 Decision Log로 기록한다.

| 변경 종류 | DEC ID 예시 |
|---|---|
| 사람 합류 | `DEC-202605-010-onboard-kim` |
| 포지션 신설 (메타) | `DEC-202605-011-add-data-engineer` |
| 권한 임시 상향 | `DEC-202605-012-temp-l3-grant-be` |
| 워크플로 게이트 강화 | `DEC-202605-013-tighten-g6` |

이 로그가 쌓이면 1년 후 "왜 우리 팀은 이렇게 운영하지?"에 답할 수 있다.

---

## 9. 변화 관리 체크리스트 (분기)

- [ ] `docs/team.md`가 실제 인원과 일치하는가
- [ ] 이탈자의 미인수 WU/산출물이 남아있지 않은가
- [ ] 포지션별 에이전트 인스턴스 수가 적정한가 (병렬화 한계 5)
- [ ] 임시 권한 상향 중 만료 기간 지난 것이 있는가
- [ ] 프로젝트 한정 워크플로(`local-*`) 중 메타 리포로 승격 가능한 패턴이 있는가
- [ ] 팀 변화 관련 Decision Log가 누락되지 않았는가
