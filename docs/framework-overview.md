# Framework Overview

## 1. 무엇을 해결하는가

기존 사내 협업의 문제:

- 포지션별 R&R이 암묵지로만 존재 → 신규 인원/에이전트 온보딩 비용이 큼
- 산출물 양식이 팀마다 달라 재사용·검증이 어려움
- AI 에이전트를 도입할 때 "어디에 어떻게" 끼워 넣을지 합의가 없음

본 프레임워크는 **포지션 = 역할 = 에이전트**로 매핑할 수 있도록 R&R, 인풋·아웃풋, 협업 규약을 표준화합니다.

## 2. 운영 모델

### 2.1 3계층 구조

```
┌─────────────────────────────────────────────────────────┐
│  Layer 3 — Human Oversight  (의사결정·승인·책임)        │
├─────────────────────────────────────────────────────────┤
│  Layer 2 — Agent Roles      (포지션별 실행 에이전트)    │
│  PM · Designer · FE · BE · QA · DevOps · Data · TL      │
├─────────────────────────────────────────────────────────┤
│  Layer 1 — Shared Protocol  (메시지 · 산출물 · 저장소)  │
└─────────────────────────────────────────────────────────┘
```

- **Layer 1**: 공통 규약·산출물 스키마·저장소(본 레포)
- **Layer 2**: 각 포지션 R&R을 따르는 단일 책임 에이전트
- **Layer 3**: 에이전트의 산출물을 검토·승인하는 사람(또는 권한 위임받은 상위 에이전트)

### 2.2 작업 단위(Work Unit)

모든 업무는 다음 5개 슬롯으로 정규화됩니다.

| 슬롯 | 설명 | 예시 |
|---|---|---|
| Goal | 달성해야 할 결과 | "결제 실패율 1% 미만" |
| Inputs | 필요한 사전 산출물 | PRD, API 스펙 |
| Owner | 책임 포지션(에이전트) | Backend Engineer |
| Deliverables | 산출물 + DoD | Tech Spec, PR |
| Reviewers | 검토 포지션 | Tech Lead, QA |

## 3. 라이프사이클

```
Kickoff → Discovery → Spec → Build → Verify → Ship → Retrospect
   PM       Design     TL    Eng     QA      DevOps    All
```

각 단계의 진입·종료 조건은 `workflows/`에 정의되어 있습니다.

## 4. 도입 가이드(요약)

1. 프로젝트 헌장(Charter) 작성 — `agents/agent-charter-template.md`
2. 활성화할 포지션 선택 — 작은 프로젝트는 PM·FE·BE·QA만으로도 시작 가능
3. 각 에이전트에 R&R 문서를 컨텍스트로 주입
4. 첫 작업을 `workflows/feature-development.md` 흐름으로 실행
5. 회고에서 R&R·규약을 보정하여 반영

## 5. 성공 지표

- 신규 프로젝트 킥오프 → 첫 산출물까지 리드타임
- 핸드오프당 재작업률
- 산출물 DoD 통과율
- 사람 검토자 1인당 처리 가능한 에이전트 작업 수
